算法思路总览
01
举例子
先拿具体例子推演几遍，把抽象问题具象化。很多思路在例子中自然浮现。
02
匹配模型
寻找熟悉的算法模型或模型变种，把实际问题往已知问题上抽象。熟练度决定匹配速度。
03
简化和泛化
先解决简化版本（如假设数据无重复、只有正数），再推广到一般情况。或反过来：将问题泛化为更一般的场景再考虑通解。
04
递推从 Base 起
从 n=0/1 的 base 情况开始，推演 n→n+1 的递推关系。DP 的本质就是找这一步。
05
数据结构头脑风暴
快速遍历所有数据结构，根据操作特征过滤：需要快速查找？→ HashMap；需要有序？→ TreeMap；需要 LIFO？→ Stack… 最差也有暴力搜索法兜底。
思维习惯
  • 熟练度优先。 大致知道思路 ≠ 能用。常用算法和数据结构要能随手写出，包括复杂度、空间要求、大数据下的表现。各种下标处理是易错点（如 find k largest number）。
  • 理解建立在熟练之上。 理解算法的本质功能才能做组合创新（如 LRU Cache = Hash + 双链表）。多变量复杂度时要按变量分别讨论。
  • 优化的本质是利用历史计算。 不管 DP 还是滑动窗口，核心都是避免重复计算。空间换时间是最常用的 trade-off。
工程实践
  • 指针排序：当排序时拷贝/移动对象的代价很高时，用指针/引用的方式排序，只移动指针。
  • 特定场景选特定结构：斐波那契堆在稠密图中做单源最短路径比二叉堆更快。大数据下常量级的改变也可能带来质的提升。
  • 时空约束折中：工程上常有时空上的特殊约束，考虑在时间上或空间上做优化（压缩、缓存、近似算法）。
  • 内外存结合：当内存不够时，考虑怎样利用磁盘存储和分批处理。
  • 测试习惯：设计测试 case 是经验积累。边界条件、空输入、大量重复、分布不均——覆盖面要广。

BST vs Hashtable：两种查找结构对比

对比焦点：BST（TreeMap/TreeSet）和 HashTable（HashMap/HashSet）都能做「查找」， 但 BST 维护了元素的有序性，而 Hashtable 追求单次查找速度。选择的关键在于是否需要「顺序相关」的操作。
维度BST (TreeMap / TreeSet)HashTable (HashMap / HashSet)
查找 O(log n) — 红黑树平衡查找 O(1) 平均 · O(n) 最差（哈希碰撞）
插入 / 删除 O(log n) — 需旋转维持平衡 O(1) 平均
元素有序遍历 O(n) — 中序遍历即有序 O(n log n) — 需额外排序
Range Query
(查找 [a, b] 范围内的所有元素)		 O(log n + k)
找到下界后中序遍历 k 个后继		 O(n) — 必须全表扫描，逐个判断
Min / Max O(log n) — 最左/最右叶子 O(n) — 需遍历全部
Floor / Ceiling
(找到 ≤x 的最大元素 或 ≥x 的最小元素)		 O(log n) — TreeMap 原生支持 不支持，无 API
Rank (求第 k 小) 可扩展支持（节点存 size） 不支持
空间开销 更大：左右子节点指针 + 颜色标记 + 父指针 较小：数组 + 链表/红黑树（碰撞桶）
常数因子 较大：树旋转、比较操作、对象封装 小：直接 hash + 数组寻址
适用场景 需要范围查询、有序遍历、最值、排名 只需快速等值查找、去重、计数
核心结论：
  • 只需要 get/put/contains → HashMap，O(1) 更快更省空间。
  • 需要 Range Query、有序遍历、Floor/Ceiling → TreeMap，BST 的有序性不可或缺。
  • 「Range Query」是区分两者的关键分水岭：Hashtable 在范围查找上等同于全表扫描，而 BST 只需找到下界后沿着中序后继走 k 步即可。
面试技巧：当遇到需要「查找值且按顺序输出」或「范围筛选」的问题时，提到「BST 的 inorder traversal 可以 O(n) 输出有序结果，而 HashMap 需要 O(n log n) 排序」是一个很好的切入点。

排序算法比较

排序本质：comparing-based 排序的极限是 O(n log n)，因为决策树有 n! 个叶子，树高至少 log(n!) ≈ n log n。Bucket Sort 之类不以比较为基础的可以做到 O(n)。
算法平均最差最好空间稳定关键要点
Bubble Sort O(n²) O(n²) O(n) O(1) ✓ 相邻两两交换；部分排序场景有独特用处——可提前退出（无交换时）
Selection Sort O(n²) O(n²) O(n²) O(1) ✗ 每次选最小放前面；部分排序时也有独特用处；不论数据分布总是 n²
Shell Sort O(n log n)~O(n^{4/3})
视 gap 序列而定		 O(n^{4/3})~O(n²) O(n log n) O(1) ✗ 插入排序的改进：先粗粒度间隔排序，再逐步缩小间隔；原地排序
Quick Sort O(n log n) O(n²) O(n log n) O(log n)~O(n)
递归栈		 ✗ 分治：选 pivot，分区，递归左右。
最差情况：数组有序时，pivot 每次都把数组分成 1 和 n-1 → S(n)=S(n-1)+O(n) → O(n²)。
迭代版：用栈保存 [left, right] 范围，不断 pop 处理（geeksforgeeks iterative quick sort）。
平均递推：S(n) = 2S(n/2) + O(n)
Merge Sort O(n log n) O(n log n) O(n log n) O(n) ✓ 始终对半分 → S(n) = 2S(n/2) + O(n) → 总是 O(n log n)，无最差情况。
代价：需要 O(n) 额外空间（合并两个有序序列时临时存储）。
链表归并：无需额外空间，但注意找到中间节点后要置 mid.next = null，否则递归不会终止。
Heap Sort O(n log n) O(n log n) O(n log n) O(1) ✗ 建堆 O(n)，每次弹堆顶 O(log n)；原地排序，不稳定
Bucket Sort O(n + k) O(n²) O(n + k) O(n + k) ✓ 非比较排序；数据均匀分布时 O(n)；k 个桶，分布不均时退化为 O(n²)
复杂度递推核心：
  • 快排平均 — S(n) = 2S(n/2) + O(n) → O(n log n)（每次大约对半分）
  • 快排最差 — S(n) = S(n-1) + O(n) → O(n²)（每次分成 1 和 n-1）
  • 归并始终 — S(n) = 2S(n/2) + O(n) → O(n log n)（总是对半分）
  • 比较排序极限 — 决策树模型，n! 个叶子 → 树高 Ω(n log n)
选型指南：
  • 数据几乎有序 → Bubble Sort 可提前退出到 O(n)
  • 日常使用 → Quick Sort（平均最快，但留意最差情况退化）
  • 需要稳定、最差也有保证 → Merge Sort（链表上还省空间）
  • 空间敏感、要 O(1) → Heap Sort 或 Shell Sort
  • 数据范围小且均匀 → Bucket Sort 能做到 O(n)

工程常用数据结构和算法

工程视角：生产环境中的数据结构往往服务于特定场景——Geohash 解决地图搜索，跳表用于高效有序集合，B 树家族是数据库和文件系统的基石。它们的核心思路是在「读写速度」「空间占用」「I/O 次数」之间做工程权衡。

Geohash — 地理空间索引

核心思想：将二维经纬度编码为一维字符串，使地理上相邻的点在编码上也相邻（前缀匹配即代表区域邻近）。
维度说明
编码方式纬度(−90,90) 和经度(−180,180) 各自二分逼近，交叉组合后 Base32 编码。每次二分取 0/1，交替组合成 bit 串 → Base32 → 字符串
层数 / 精度每增加一位，网格缩小。1 位 ~ 5,000km，8 位 ~ 19m，12 位 ~ 0.06m。字符串越长精度越高
周边搜索对目标点的 Geohash 做前缀匹配即可找到邻近区域。配合多层分片索引：先按粗粒度前缀分片，再在片内细粒度匹配——用空间换时间
局限性边界突变：相邻物理位置可能在编码上相差很远（跨 Geohash 格子边界时）。通常需要取周围 8 个邻格做补充搜索
常见应用美团 / 大众点评「附近商家」、Uber 派单、滴滴定位索引、Elasticsearch Geo Query

Skip List (跳表)

核心思想：在有序链表上叠加「多层索引」层，用概率平衡代替严格平衡。以 O(log n) 的平均代价实现查找、插入、删除。
维度说明
结构底层是完整有序链表，上层是稀疏索引（每 k 个节点提取一个到上一层）。查找时从顶层开始逐层向下"跳跃"
查找从最高层头节点开始，向右找到最后一个 ≤ target 的节点，再降一层继续 → 平均 O(log n)
插入先用查找找到插入位置，然后随机决定提升到哪一层（概率 ½ 提升一层、¼ 提升两层…）
空间额外指针平均约 O(n)，实际中每个节点平均 2 个指针（推导：∑(½)^(k-1) = 2）
对比平衡树实现简单、无旋转/rebalance；范围查询友好（底层链表顺序遍历即可）；Redis ZSET 的底层实现正是跳表/td
对比 B 树跳表数据在内存，B 树针对磁盘 I/O 优化；跳表写冲突少、适合高并发

B-Tree (B-树) — 磁盘查找的基石

背景：普通二叉查找树（红黑树等）在内存中表现优秀，但数据量超出内存时，每次节点访问都可能触发一次磁盘 I/O。B-Tree 通过将单个节点设计为等于一个磁盘页，使树高极小（通常 ≤ 3），从而大幅减少 I/O 次数。

定义：一棵 m 阶 B-Tree 满足以下性质：

  1. 每个结点至多有 m 棵子树（即 m-1 个关键码）
  2. 根结点若不是叶子，则至少有 2 棵子树
  3. 除根外，所有非终端结点至少有 ⌈m/2⌉ 棵子树
  4. 非终端结点结构：(n, A₀, K₁, A₁, K₂, …, Aₙ)，其中 Kᵢ 为关键码且 Kᵢ < Kᵢ₊₁，Aᵢ 指向子树根结点，Aᵢ₋₁ 子树中所有关键码 < Kᵢ
  5. 所有叶子结点出现在同一层（外部结点，查找失败结点），树高等于路径长度
高度的严格上界：对于 n 个关键码的 m 阶 B-Tree，最坏情况树高不超过 log⌈m/2⌉((n+1)/2) + 1。推导：
每层最少结点数：根 1 个 → 第 2 层 ≥ 2 个 → 第 3 层 ≥ 2⌈m/2⌉ → 第 J+1 层 ≥ 2⌈m/2⌉J-1，而 J+1 层是叶子层（共 n+1 个叶子）→ n+1 ≥ 2⌈m/2⌉J-1 → J ≤ 1 + log⌈m/2⌉((n+1)/2)。

磁盘 I/O 优化设计：

  • 每个结点大小等于一个磁盘页（通常 4KB），一次 I/O 即可载入整个结点
  • 根结点常驻内存，查找最多需 h-1 次 I/O（h 为树高）
  • m 通常 > 100，因此 h ≤ 3，即 最多 2~3 次 I/O 即可找到目标
  • 红黑树 h ≈ O(log₂ n)，对 100 万数据 h ≈ 20，每次 I/O 读一个节点 → 20 次 I/O，远慢于 B-Tree

B+Tree — 文件系统的索引标准

与 B-Tree 的核心差异：

维度B-TreeB+Tree
内部结点内容 存关键码 + 数据 / 指针 只存关键码索引，不存数据；一个页能容纳更多关键码 → m 更大 → 树更矮
叶子结点内容 部分关键码指向实际记录 全部关键码出现在叶子层，且叶子结点包含指向实际记录的指针
子树与关键码数 n 棵子树含 n 个关键码 n 棵子树含 n 个关键码
叶子间连接 无 叶子结点链表化——按关键码大小顺序连接，支持高效范围查询和顺序遍历
查找行为 在内部结点找到等于 K 的关键码即终止 必须走到叶子结点才终止（即使内部结点相等也继续向下）
两种查找方式 只有从根开始的随机查找 双头指针：一个指向根（随机查找），一个指向最小关键字叶子（顺序查找）
范围查询性能 找到下界后需回溯到父结点找后继 → 多次 I/O 找到下界后，沿叶子链表顺序遍历即可 → 只需少量 I/O

红黑树 (Red-Black Tree) — 内存中的平衡 BST

定位：红黑树是内存中最广泛使用的平衡二叉搜索树。Java TreeMap/TreeSet、C++ std::map、Linux 内核调度器、epoll 的事件管理、Nginx 的定时器都基于红黑树。

5 条核心性质（保持平衡的约束）：

  1. 每个节点是红色或黑色
  2. 根节点是黑色
  3. 叶子节点（NIL）是黑色
  4. 红色节点的子节点必须是黑色（即不存在连续红色）
  5. 从任一节点到其子孙叶子的所有路径包含相同数量的黑色节点（黑高相等）
平衡性保证：约束 4+5 确保了 最长路径 ≤ 2 × 最短路径。最短路径全黑，最长路径红黑交替，树高 ≤ 2 log₂(n+1) → 所有操作 O(log n)。
维度红黑树AVL 树
平衡程度弱平衡：最长路径 ≤ 2×最短路径严格平衡：左右子树高差 ≤ 1
树高≤ 2 log₂(n+1)≈ 1.44 log₂(n+1)
查找O(log n)O(log n)，常数略优（树更矮）
插入/删除O(log n)，常数小：最多 3 次旋转O(log n)，常数大：可能 O(log n) 次旋转
工程选型写多读少的通用场景
Java TreeMap、C++ map、Linux 内核		读多写少的字典
数据库索引（内存级）

插入与删除的核心逻辑：

  • 插入（节点标记为红色）：仅需检查是否违反「无连续红色」→ 必要时变色 + 旋转，最多 2 次旋转即可修复
  • 删除：如果删除的是黑色节点，会破坏「黑高相等」→ 分情况调整（"双黑"修复），最多 3 次旋转
工程价值：红黑树在「写操作频繁」的场景下远优于 AVL 树，因为 AVL 在插入/删除后可能触发 O(log n) 次旋转，而红黑树只触发常数次。这也是 Java TreeMap / C++ std::map 选择红黑树而不是 AVL 树的原因。

常见应用场景：

  • Java TreeMap / TreeSet — 底层红黑树，提供 key 有序的 Map/Set
  • Linux 内核完全公平调度器 (CFS) — 用红黑树管理可运行进程，按 vruntime 排序
  • Linux epoll — 用红黑树管理所有注册的 fd 及其事件
  • Nginx 定时器 — 用红黑树按超时时间排序，快速找到最早到期的定时事件
  • HashMap 碰撞处理 — Java 8+ 中当链表长度 > 8 时转为红黑树，将最差查找从 O(n) 降到 O(log n)

Range Query — 工程中的范围查询

本质：范围查询是指「查询满足某个范围条件的一批记录」，例如 WHERE age BETWEEN 20 AND 30（数值范围）、WHERE time > '2024-01-01'（时间范围）、WHERE name > 'Li' AND name < 'Liu'（字典范围）。它与区间和/最值的区别在于：这里要获取记录本身，而非一个聚合值。

范围查询的核心挑战：无序存储下找范围数据 = 全表扫描。有索引才能高效。

场景核心结构关键机制工程实例
数据库单字段范围查询 B+Tree 索引 利用 B+Tree 叶子节点的双向链表：找到第一个满足条件的记录后，沿链表顺序扫描即可。复杂度 ≈ O(log n + k)，k 为结果数。 MySQL InnoDB：WHERE age > 18 AND age < 60
多字段范围查询 复合索引 + 最左前缀 范围条件只能用到一个索引列，后续列无法走索引。比如 (city, age) 上查 city='BJ' AND age BETWEEN 20 AND 30：city 走索引，age 在 city 的索引段内做遍历 MySQL 复合索引设计、MongoDB 复合索引
二维空间范围
（矩形框选附近的点）		 Geohash / R-Tree Geohash 用前缀匹配代替二维范围扫描；R-Tree 用最小外包矩形 (MBR) 递归划分空间 Meituan 附近商家、PostGIS、Elasticsearch Geo Query
区间重叠查询
（找到所有与某区间重叠的区间）		 Interval Tree 以区间中点为界，左右子树分别存完全在左侧和完全在右侧的区间，跨越中点的单独存。查找时根据查询区间的位置选择遍历方向。 会议室预定冲突检测、网络包过滤规则匹配（iptables 规则链）
低基数范围统计
（枚举值上的范围计数）		 Bitmap Index 每个取值一个 bitmap（位图），长度为总记录数。范围查询 = 多个 bitmap 的 OR/AND 运算。位图计算远快于行扫描。 Druid、ClickHouse、Oracle Bitmap Index（数据仓库场景）
时间序列范围查询 Time-Partitioned LSM-Tree 按时间粒度分片（每小时/每天一个 SSTable），用时间分区裁剪（partition pruning）直接跳过无关分区。LSM-Tree 内部用布隆过滤器加速不存在的 key 判断。 InfluxDB、Prometheus、Elasticsearch 时间索引
分布式系统中的范围分片 Range Partitioning 按 key 范围分片（如 [a, f) → shard1, [f, m) → shard2...），每个分片内部用 B+Tree 或 LSM-Tree 组织。查询时路由到相关分片，必要时合并结果。 Bigtable / HBase / CockroachDB / MongoDB sharding
核心原则：范围查询的效率取决于数据在物理存储上的有序性。如果数据按查询字段的序物理存储（clustered index），范围扫描就只需要顺序 I/O（极快）；否则需要大量随机 I/O（极慢）。这就是 InnoDB 主键用聚簇索引、覆盖索引能提升范围查询性能的根本原因。
MySQL 范围查询优化关键：
  • 索引下推 (ICP) — MySQL 5.6+ 将 WHERE 条件中索引可过滤的部分下推到存储引擎层，减少回表次数
  • MRR (Multi-Range Read) — 将随机 I/O 的 secondary index 回表变成批量顺序 I/O
  • 覆盖索引 (Covering Index) — 索引包含所有查询列，避免回表 → 最极致的范围查询优化
  • 分析 EXPLAIN 中 type 列：range > ref > ALL，range 表示使用了索引范围扫描
工程选型对比：
  • 单字段范围 → B+Tree 索引（MySQL/MariaDB/PostgreSQL 默认）
  • 二维空间范围 → Geohash（简单有效）或 R-Tree（精确度更高）
  • 区间重叠（interval stabbing） → Interval Tree（O(log n + k)）
  • 低基数枚举值范围统计 → Bitmap Index（O(1) 位运算）
  • 时间序列范围 → 时间分区 + LSM-Tree（InfluxDB、Prometheus）
  • 分布式范围查询 → Range Partitioning + 分片裁剪（HBase、CockroachDB）

4.7 总结：为什么数据库索引用 B+Tree 而不是红黑树

根本原因：磁盘 I/O 次数是瓶颈，而 B+Tree 的树高极小。
结构树高（n=10⁶）I/O 次数/查询能否利用局部性
红黑树≈ log₂ 10⁶ ≈ 20最多 20 次✗ — 逻辑相邻的节点物理上可能不连续
B-Tree (m=500)≈ log₅₀₀ 10⁶ ≈ 2~32~3 次✓ — 每个节点是一个页
B+Tree (m=500)≈ 2~3（内部节点只存索引，m 更大）2~3 次✓ — 且范围查询时叶子链表顺序读取

原理补充：磁盘预读与局部性

  • 磁盘读取一次数据的时间由寻道时间 + 旋转延迟 + 传输时间组成，远慢于内存。
  • 操作系统利用局部性原理按页（4KB）预读：即使只取 1 字节，也会将整个页读入内存。
  • B-Tree/B+Tree 将结点大小设计为等于一个页，一次 I/O 即可载入整个结点。
  • 红黑树反之：逻辑上相邻的父子节点在物理磁盘上可能相距很远，无法利用预读。
工程选型总结：
  • Geohash → 地理空间「附近的人」搜索
  • Skip List → 内存中的有序集合（Redis ZSET）、高并发场景
  • 红黑树 → 内存中的通用有序容器（TreeMap、epoll、CFS 调度器）
  • Range Query 算法 → 数据库范围查询、Interval Tree、Bitmap Index
  • B-Tree → 通用磁盘索引，单点查询为主
  • B+Tree → 现代数据库索引首选（MySQL InnoDB），范围查询和顺序遍历更优

经典数据结构详解

定位：堆、Trie、并查集、线段树是算法面试中最高频的自定义数据结构。它们不依赖外部库，需要手写实现。掌握它们的原理、实现和复杂度是面试基本要求。

Heap (堆) — 优先队列的工程形态

本质：堆是一棵完全二叉树，满足父节点 ≤ 子节点（小顶堆）或父节点 ≥ 子节点（大顶堆）。工程中通常用数组存储（i 的子节点为 2i+1 和 2i+2）。

建堆 (Build Heap) — O(n) 的推导：

建堆有两种方式：
1. 逐个插入（插入法）：每个元素插入到末尾后上浮 (siftUp)，n 个元素 → O(n log n)
2. 自底向上建堆（Floyd 方法）：从最后一个非叶子节点开始下沉 (siftDown)，复杂度 O(n)

为什么 Floyd 方法是 O(n)？
  高度为 h 的节点最多有 n/2^(h+1) 个，每个下沉操作最多走 h 步
  ∑[h=0 → log n] (n/2^(h+1)) × h  < n × ∑(h/2^h) = O(n)
  因为 ∑(h/2^h) = 2（收敛常数），所以总操作 < 2n = O(n)

结论：Floyd 建堆的交换次数 = n - (叶子数) ≈ n，约 n/2 次交换，线性时间。
操作复杂度说明
建堆 (Build)O(n)Floyd 自底向上法；逐个插入是 O(n log n)
插入 (Insert)O(log n)先放末尾，然后 siftUp（上浮）
取堆顶 (Peek)O(1)直接返回 arr[0]
删除堆顶 (Poll)O(log n)末尾元素移到堆顶后 siftDown（下沉）
删除任意 (Delete)O(log n)先用该节点跟末尾换，再做 siftUp 或 siftDown
Java 实现：PriorityQueue<T> 默认小顶堆，通过 Comparator.reverseOrder() 转大顶堆。
注意：PriorityQueue 的 iterator 不保证顺序；建堆用 new PriorityQueue<>(collection) 才是 O(n) 的 Floyd 建堆，逐个 add 是 O(n log n)。

Trie (前缀树) — 字符串的高速索引

本质：Trie (Prefix Tree) 是一种多叉树结构，用于高效地存储和检索字符串集合中的键。核心思路是利用字符串的公共前缀来节省空间和查找时间。
实现要点：
  • 根节点不存放任何字符。 根节点是空入口，不表示任何前缀。
  • 信息在边上（children 字典里）。 每个节点的 children map 的 key 代表从父节点到子节点的边上字符，key 所对应的子节点代表「从根到该节点路径上经过的字符序列」。换句话说，节点本身不存 char，char 体现在边的选择上。
  • 终止标记：每个节点维护一个布尔标记 isEnd，表示从根到当前节点的路径是否构成一个完整的单词。同一个词可以作为其他词的前缀（如 "in" 和 "inn"）。

删除操作 — 复杂且少用：

删除一个单词时，不能直接释放节点，因为它可能被其他单词共享。
删除是递归的：
1. 从根开始，沿着单词的字符路径递归查找到底
2. 在返回过程中，检查当前节点的引用计数（子节点数目）
3. 如果当前节点的引用计数从 1 → 0（即删除后没有子节点了），并且该节点也不是其他单词的终点
   则可以释放该节点（级联释放）
4. 这就是为什么实际工程中 Trie 的删除实现很少见——Node 通常没有 ref count，实现级联释放需要额外维护

大多数场景下 Trie 只做插入和查询，不做删除。如果需要删除，通常使用 软删除（标记删除）或重建。

Double-Array Trie — 中文 NLP 的核心：

  • 基于 base[] + check[] 两个数组实现的 Trie，用 静态数组代替动态指针/Map
  • 查找时只需两次数组访问：base[state] + c = next; check[next] == state，效率极高
  • 广泛用于中文自然语言处理：中文词表的前缀批量查找和精确匹配，比如中文分词中的词表匹配（正向最大匹配、逆向最大匹配）
  • 典型的 Java 实现：org.ahocorasick.trie（AC 自动机），com.hankcs.algorithm.AhoCorasickDoubleArrayTrie（HanLP）
  • 相比 HashMap：Trie 支持前缀搜索（查找所有以 "北京" 开头的词），而 HashMap 只能做精确查找

Union-Find (并查集) — 动态连通性

本质：并查集是一种树形的数据结构，用于处理不相交集合 (Disjoint Set) 的合并与查询问题。支持两种操作：find(x) 查找 x 属于哪个集合，union(x, y) 合并 x 和 y 所在的集合。
核心优化（二者结合使单次操作近似 O(α(n))）：
  • 路径压缩 (Pa — 在 find 操作中，将路径上所有节点直接指向根节点，使后续查找几乎 O(1)
  • 按秩合并 (Union by Rank/Size) — 将较小的树合并到较大的树上，保证树高不超过 O(log n)
  • 反阿克曼函数 α(n) — 两种优化结合后，单次操作的均摊复杂度为 O(α(n))，其中 α(n) 增长极慢（α(宇宙中原子数) ≈ 5），实际可视为常数

代码模板（5 行核心）：

class UnionFind {
    int[] parent, rank;                    // parent[x] = x 初始化时指向自己
    public int find(int x) {
        if (parent[x] != x) parent[x] = find(parent[x]); // 路径压缩
        return parent[x];
    }
    public void union(int x, int y) {
        int rx = find(x), ry = find(y);
        if (rx == ry) return;
        if (rank[rx] < rank[ry]) parent[rx] = ry;  // 按秩合并
        else if (rank[rx] > rank[ry]) parent[ry] = rx;
        else { parent[ry] = rx; rank[rx]++; }
    }
}
场景说明
图连通分量经典场景：判断图中节点是否连通、计算连通分量个数
冗余连接LeetCode 684 — 在图中找到一条多余的边，去掉后变成树
Kruskal 最小生成树按边权重排序后，用 Union-Find 判断两端是否已连通
等价关系朋友圈问题、方程式变量分组
动态连通性社交网络好友关系、P2P 网络节点发现、动态图连通性

Segment Tree (线段树) — 通用区间查询结构

本质：线段树是一棵二叉树，每个节点代表一个区间 [l, r]，左右子节点分别代表 [l, mid] 和 [mid+1, r]。所有叶子节点是长度为 1 的区间（即数组的单个元素）。适合对数组进行区间聚合查询 + 区间更新的场景。

核心操作：

操作复杂度说明
建树 (Build)O(n)从叶子向上递归构建；数组大小为 4n（最坏情况取 4 倍空间）
区间查询 (Query)O(log n)从根向下，完全覆盖的节点直接返回，否则递归左右子树
单点更新 (Point Update)O(log n)递归到叶子修改后向上回溯更新所有父节点
区间更新 (Range Update)O(log n)需要配合懒标记 (Lazy Propagation)：延迟下推更新，避免 O(n)
懒标记 (Lazy Propagation) 核心思想：
  1. 更新一个区间时，不立即更新所有叶子，而是在完全覆盖的节点上打标记，并更新该节点的聚合值
  2. 只有当后续查询或更新需要深入到某个节点的子区间时，才将标记下推 (pushDown) 到子节点
  3. 这样保证了每个操作最坏只需要访问 O(log n) 个节点

常见变体：

  • 离散化 + 线段树 — 当值域很大时，先用坐标压缩再建树，减少空间
  • 动态开点线段树 — 不预先建树，只在需要时创建节点，适合值域极大但操作不多的场景（如 n > 10⁹ 的区间赋值）
  • 权值线段树 — 下标代表值域，用于求第 K 小/大、逆序对
  • 可持久化线段树 (Persistent Segment Tree / 主席树) — 保存所有历史版本，用于静态区间第 K 小
  • 线段树 + 扫描线 — 矩形面积并 / 周长并
选型对比：
  • 只需要区间求和，无需更新 → Prefix Sum (O(1))
  • 只需要区间求和，有单点更新 → Fenwick Tree (代码短、常数小)
  • 需要区间最值 / 复杂聚合，需区间更新 → Segment Tree
  • 没有更新时只做 RMQ → Sparse Table (O(1) 查询、不能更新)

图 (Graph) 的表示与算法

图的核心问题：图的表示（如何存）、图的遍历（BFS/DFS）、最短路径（Dijkstra、Floyd、Bellman-Ford）、最小生成树（Kruskal、Prim）。选对表示方式是解决后续所有图问题的基础。

邻接矩阵 (Adjacency Matrix)

用一个 V × V 的二维数组 表示图，edges[i][j] 表示节点 i 到节点 j 的边（无权图用 0/1，有权图用权值）。

维度说明
存储空间O(V²) — 固定开销，与边数 E 无关。无向图是对称矩阵，可只存一半：1+2+...+(V-1) = V(V-1)/2
判断两边是否有边O(1) — 直接 edges[i][j] 取值即可
入度 / 出度扫描某行（出度）或某列（入度）→ O(V)
统计总边数扫描整个矩阵 → O(V²)
遍历某节点的所有邻居扫描对应行 → O(V)
典型定义： 
class AdjMatrixGraph {
    int[] v;                    // 顶点数组
    int[][] edges;              // 邻接矩阵
    int n, e;                   // 顶点数、边数
}

重要：需要人为给每个节点定义一个编号（按添加顺序 0, 1, ..., n-1），通过编号访问矩阵。

邻接表 (Adjacency List)

对每个顶点维护一个链表或动态数组，存储所有从该顶点出发的边。类似哈希表的结构。

维度说明
存储空间V 个头节点 + 无向图 2E 个边节点 / 有向图 E 个边节点
出度直接取头节点对应链表的长度 → O(1) 或 O(度数)
入度需要扫描整个邻接表 → O(V+E)。又因此出现了逆邻接表：存储指向本节点的所有节点信息
判断两边是否有边遍历对应链表 → O(度数)，最差 O(V)
统计总边数遍历所有链表 → O(V+E)
遍历某节点的所有邻居直接遍历对应链表 → O(度数)
典型定义： 
class Node {                    // 边节点
    int adjIndex;               // 邻接节点编号
    int weight;                 // 权值
    Node next;                  // 指向下一条边
}

class VertexNode {             // 顶点节点
    int info;                  // 顶点信息
    Node next;                 // 邻接表头指针
}

class AdjListGraph {
    VertexNode[] vertices;     // 顶点数组
    int n, e;                  // 顶点数、边数
}

邻接矩阵 vs 邻接表

维度邻接矩阵邻接表
空间 O(V²) — 固定开销 O(V+E) — 与边数成正比
判断 (u, v) 是否有边 O(1) O(degree(u))
遍历所有邻居 O(V) — 必须扫描整行 O(degree(v)) — 直接遍历链表
添加 / 删除边 O(1) — 直接改矩阵元素 O(degree) — 需维护链表
添加新顶点 O(V²) — 需重建矩阵 O(1) — 追加头节点即可
图密度 稠密图（E ≈ V²）更合适 稀疏图（E ≈ V）更合适
图类型 静态图（建好后不变） 动态图（频繁增删节点/边）
选型建议：
  • 稀疏图（E 远小于 V²）→ 邻接表，节省空间且遍历邻居高效
  • 稠密图（E ≈ V²）→ 邻接矩阵，O(1) 判边，实现简单
  • 邻接矩阵的稀疏存储方式：三元组 (row, col, value) 可压缩稀疏矩阵
  • 工程实践：竞赛/面试中常用 List<List<Integer>> graph（Java）或 vector<int> graph[]（C++）作为邻接表

对象和指针的表示方式

直接将节点定义为对象，边通过直接引用表示。本质上类似于邻接表，但更贴近面向对象思维。

表示方式： 
class Vertex {
    int id;
    List<Vertex> neighbors;   // 直接指向相邻节点对象
}

// 使用时：
Vertex v1 = new Vertex(1);
Vertex v2 = new Vertex(2);
v1.neighbors.add(v2);        // 添加一条边 v1 → v2
// 如果是无向图，还需 v2.neighbors.add(v1)

这种方式在算法竞赛/面试中较少使用（对象开销大），但在工程系统中更自然。在 Java 中通常用 List<List<Integer>> 替代，性能更好。

Dijkstra 最短路径算法

场景：单源最短路径，所有边权为非负。核心思想：贪心 —— 每次从未访问的节点中选 dist 最小的节点加入已访问集合，然后更新其邻接节点的 dist。
算法框架（基于邻接矩阵）： 
void dijkstra(int n, int v, int[] dist, int[] prev, int[][] c) {
    // n: 顶点数, v: 源点, dist: 距离数组, prev: 前驱数组, c: 邻接矩阵
    boolean[] s = new boolean[n];    // s[i] = true 表示已加入集合
    int MAX = Integer.MAX_VALUE;

    // 1. 初始化：从源点 v 直接出发的距离
    for (int i = 0; i < n; i++) {
        dist[i] = c[v][i];
        s[i] = false;
        prev[i] = (dist[i] == MAX) ? -1 : v;
    }
    dist[v] = 0;
    s[v] = true;

    // 2. 循环 n-1 次，每次加入一个节点
    for (int i = 1; i < n; i++) {
        // 2a. 找到当前未访问节点中 dist 最小的
        int u = -1, minDist = MAX;
        for (int j = 0; j < n; j++) {
            if (!s[j] && dist[j] < minDist) {
                u = j;
                minDist = dist[j];
            }
        }
        if (u == -1) break;          // 剩余节点不可达
        s[u] = true;                  // 2b. 加入已访问集合

        // 2c. 松弛：更新 u 的所有邻接节点的距离
        for (int j = 0; j < n; j++) {
            if (!s[j] && c[u][j] < MAX) {
                int newDist = dist[u] + c[u][j];
                if (newDist < dist[j]) {
                    dist[j] = newDist;
                    prev[j] = u;     // 记录路径
                }
            }
        }
    }
}
复杂度与优化：
  • 朴素实现（邻接矩阵）：O(V²) — 每次找最小 dist 需扫描所有节点
  • 堆优化（邻接表 + PriorityQueue）：O((V+E) log V) — 用堆维护未访问节点中的最小 dist，适合稀疏图
  • prev 数组的作用：记录最短路径的前驱节点，从目标节点出发 prev[target] 反向回溯即可得到完整路径
  • BFS 与 Dijkstra 的关系：当所有边权为 1 时，Dijkstra 退化为 BFS（队列代替优先队列）

最小生成树 (MST)

目标：在连通无向带权图中找到一棵包含所有顶点的树，使得树中所有边的权重和最小。n 个节点，n-1 条边。

克鲁斯卡尔 (Kruskal) 算法 — 从边出发

步骤说明
1. 初始化扫描边数组，建立最小堆（按权值排序）；每个堆节点为 {from, to, weight}
2. 初始化并查集每个节点自成一个集合
3. 主循环从堆中不断取出最小边，若两端不在同一集合则合并，将边加入 MST
算法框架： 
int kruskal(int n, List<Edge> edges) {
    // 1. 建最小堆（或按权值排序）
    PriorityQueue<Edge> pq = new PriorityQueue<>((a,b) -> a.weight - b.weight);
    for (Edge e : edges) pq.offer(e);

    // 2. 并查集
    UnionFind uf = new UnionFind(n);
    List<Edge> mst = new ArrayList<>();
    int i = 0;

    // 3. 主循环
    while (i < n - 1 && !pq.isEmpty()) {
        Edge e = pq.poll();
        int ru = uf.find(e.from), rv = uf.find(e.to);
        if (ru != rv) {
            uf.union(ru, rv);
            mst.add(e);
            i++;
        }
    }

    return (i == n - 1) ? totalWeight(mst) : -1; // -1 表示非连通图
}

普里姆 (Prim) 算法 — 从顶点出发

核心维护 两个数组：

  • lowest[j]：顶点 j 到生成树集合的最小权值（距离）
  • nearest[j]：顶点 j 到生成树集合中最近的顶点编号
算法框架（基于邻接矩阵）： 
// 1. 初始化：从顶点 0 开始
lowest[i] = w[0][i];      // 各顶点到初始集合 {0} 的距离
nearest[i] = 0;           // 各顶点到集合内最近的顶点是 0
nearest[0] = -1;          // -1 表示已在生成树集合中

// 2. 循环 n-1 次
for (int t = 0; t < n - 1; t++) {
    // 找不在集合中且 lowest 最小的顶点 v
    int v = -1, minVal = INF;
    for (int j = 0; j < n; j++)
        if (nearest[j] != -1 && lowest[j] < minVal) {
            v = j;
            minVal = lowest[j];
        }

    // 将边 (nearest[v], v, lowest[v]) 加入 MST
    nearest[v] = -1;         // v 加入集合

    // 3. 更新 lowest 和 nearest
    for (int j = 0; j < n; j++)
        if (nearest[j] != -1 && w[v][j] < lowest[j]) {
            lowest[j] = w[v][j];
            nearest[j] = v;
        }
}
维度KruskalPrim
出发点边（全局贪心）顶点（局部扩展）
核心数据结构最小堆 + 并查集lowest[] + nearest[]
复杂度O(E log E) — 排序边占主导O(V²) 朴素 · O((V+E) log V) 堆优化
适用场景稀疏图（E 接近 V）稠密图（E 接近 V²）
易错点：
  • 图必须是连通的才能产生 MST。Kruskal 结束后检查 i == n-1。
  • BFS 和 DFS 前要加循环，因为图可能不连通。for (int i = 0; i < n; i++) if (!visited[i]) { bfs/dfs(i); count++; }
  • Dijkstra 不适用于负权边——负权边用 Bellman-Ford 或 SPFA。
  • 邻接表实现 Dijkstra 时，优先队列中可能有过期的旧距离记录，需要 if (dist[cur] != d) continue; 跳过。

哈希表 (Hash Table)

核心思想：将关键字通过散列函数映射到数组的某个位置。理想情况下 O(1) 即可找到元素。当全集 |U| > 数组大小 m 时，必然导致碰撞，因此需要在「好的散列函数」和「解决碰撞的方法」两方面下功夫。

链接法 (Chaining)

数组的每个槽中存放一个链表头指针，碰撞的元素通过链表链接。这是最常用的方法（Java HashMap 的默认实现）。

场景时间复杂度说明
最差情况O(n)所有关键字挤在同一个槽中
平均不成功查找O(1 + n/m)查找到表项末尾，期望遍历 n/m 个元素
平均成功查找O(1 + n/m)在 n/m 长的链表中，任一元素被查找的概率为 1/长度

开放寻址法 (Open Addressing)

没有链表，所有元素都放在散列表中。插入时连续检查散列表各项直到找到空槽。检查顺序由探查序列决定：hash(key) = f(key, i)，其中 i 为探查次数。

三种探查方法： 
线性探查：   f(k, i) = (h(k) + i) mod m        → 较重的群集现象
二次探查：   f(k, i) = (h(k) + c₁·i + c₂·i²) mod m
双重散列：   f(k, i) = (h₁(k) + i·h₂(k)) mod m  → 最佳，需 h₂(k) 与 m 互质

注意：若需删除元素，每个槽要添加状态位标识「空」或「已删除」，否则查找会中断。因此需要删除时通常用链接法。m 常取 2 的幂。

散列函数

理想散列 (Simple Uniform Hashing)：每个关键字等可能地散列到 m 个槽中的任何一个，且与其他关键字散列位置无关。实际中根据关键字分布的限制性信息设计函数，先将关键字映射到自然数（如字符串用 ASCII 累加或进制基数）。
方法公式要点
除法散列法 h(k) = k mod m m 不取 2 的幂（否则等价于取 k 的低 p 位，浪费高位信息）。m 选为距离 2 的幂较远的质数。例如 n=2000、期望检查 3 个元素 → m ≈ 2000/3 ≈ 701（接近 2⁹=512 但不太近的质数）。
乘法散列法 h(k) = ⌊ m·(kA mod 1) ⌋ A 取 0 < A < 1 的常数（如 A≈0.618）。与 m 的选取无关。
全域散列 (Universal Hashing) 从一组精心设计的函数中随机选择一个 防止针对特定输入的恶意碰撞，确保最差情况也有良好期望。

文件中的哈希表

场景：实时流数据的 key/value 存储（类似 UNIX 高级环境编程或 Berkeley DB 的实现）。

实现方式：

  • 文件前 1000 个字节作为哈希表的槽（不存数据），每个槽记录一个文件偏移量 (offset)
  • 插入新值时，先 hash 到槽，按 offset 找到对应链表
  • 项格式为 Word || WordCount || next_offset（链接指针存文件 offset）
  • 追加写入文件，构建基于文件的 key/value 数据库
扩容方案：当数据量太大放不下时，将旧数据标记删除，在文件后端开辟更大空间重新存放。
Value 过大：若 value 太大放不下，将 value 存在单独文件中，链表指针改为 (文件, offset)。

哈希表的平摊分析

装载因子过高时需扩容并重新散列（因为 m 变了，所有 key 重新映射）。

每次翻倍扩容的均摊成本： 
假定表初始大小 1，每次扩张翻倍。
第 i 次插入的代价：ci = 1（正常插入）或 ci = i（当 i-1 是 2 的幂时需重新散列）

总代价 = c₁ + c₂ + ... + cₙ
       = n + 2⁰ + 2¹ + 2² + ... + 2^⌊log₂n⌋
       < n + 2n = 3n

均摊成本 = 3n / n = O(3) = O(1)

尽管单次插入可能很慢（需要重新散列所有旧元素），但均摊到每次插入只有常数代价。这正是 Java HashMap 动态扩容的理论基础。

实战选择要点

核心心法：先明确「最频繁的操作」是什么，再反过来选数据结构。
  1. 读多写少 → 数组优先。 只需要随机读，偶尔尾部追加 → ArrayList 完胜。
  2. 写多读少 → 链表或堆。 频繁插入/删除 → LinkedList；频繁取最值 → Heap。
  3. 查找密集型 → 哈希表。 绝大多数「判断是否存在」的场景，HashMap 是第一选择。
  4. 需要保持顺序 → TreeMap 或链表。 自然有序 → TreeMap；按插入顺序 → LinkedHashMap。
  5. 区间操作 → 看更新频率。 不更新 → 前缀和；单点更新 → BIT；复杂更新 → Segment Tree。
  6. 字符串匹配 → 先看问题规模。 固定词典 + 大量查询 → Trie；单次长串匹配 → KMP / Rabin-Karp。
提示：面试时说出「这个场景需要 O(1) 查找，所以我用 HashMap」已经是在展示数据结构思维。不要只背 API，要说出复杂度从哪里来。
易错点：
  • 误用 LinkedList 做随机访问（get(index) 是 O(n)！）
  • 对 HashMap 期望有序遍历（需要顺序用 TreeMap 或 LinkedHashMap）
  • PriorityQueue 的 iterator 不保证顺序（要用 poll 逐个取出）
  • TreeSet 存自定义对象要正确实现 Comparator
  • BIT 和 Segment Tree 不要在不要求动态更新的场景使用（前缀和就够）
