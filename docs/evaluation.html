表达式求值：什么时候触发结算

核心洞见：表达式求值的所有变体共享同一个循环模版——数字拼接 → 遇到触发条件 → 结算并更新状态。区别只在于触发条件和结算时哪些变量需要更新。

而整个问题的核心只有一个：理解「什么时候触发结算」。

1. 理解什么时候触发

这是全篇唯一需要真正想清楚的逻辑。其余所有变体只是换个触发符号、多几行结算代码而已。触发只有三种情形，且它们本质上是同一件事。

触发一：碰到一个新的运算符符号

数字 num 是在累积的，它属于「上一个符号」sign 管辖。一旦读到新符号，num 就攒到头了，必须先把上一次的运算结算掉，才能空出 num 给下一轮。

「碰到新符号，就是结算以前的运算」。当前符号 c 只是扳机——它自己并不参与这次结算，结算用的是上一个 sign。扣完扳机，c 取代 sign 留给下一轮。（这条对无括号的 3.1 / 3.2 成立；3.3 带括号后分派对象换成 c，见 §3.3。）

触发二：到了最后一个字符（虚拟结尾符）

表达式末尾没有运算符来「推」出结算，但最后一个 num 不能丢。所以 i == len-1 在所有变体里都出现——它相当于在末尾补了一个虚拟的结束符，同样触发一次结算。

把最后一个字符也当作一次结算触发。这正是 i == len-1 出现在每个触发条件里的原因，也是为什么这个 if 不能是 else if（否则最后一个字符是数字时会被数字分支吃掉，漏掉结算）。

触发三：最开始的符号（虚拟开头符）

同理，第一个数字前其实也隐含了一个「起点」：sign = '+'，res = 0。它等价于在表达式最前面虚拟放了一个 +，只是这个 + 不触发结算，而是作为 num 的初始归属。初始化代码就是在扮演这个虚拟开头符。

最开始的符号，相当于前置了 result = 0、sign = '+' 的预置结果。这样一来，「遇到符号就结算」这条规则对第一个数也天然成立，代码可以统一处理，不用为开头写特判。

把三个触发点连起来，整个循环的节奏就清楚了：预置 res=0, sign='+'（虚拟开头）→ 数字累积 → 遇新符号或末尾结算（结算上一次），首尾各一次虚拟触发，中间每次真实触发。

题目触发结算的条件
只有 + -+ - | i == len-1
加入 * /+ - * / | i == len-1
加入 ()+ - ( ) | i == len-1

i == len-1 出现在每一个里——最后一个数字后面没有运算符来推动结算，必须显式兜底。

注意：结算的触发条件 必须 是独立的 if（不能是 else if），否则最后一个字符是数字时会被数字分支吃掉，漏掉结算。
重要：触发结算时用的是 上一个 op（存在 sign 里），不是当前字符 c。c 只是扳机，扣动后 c 自己变成新的 sign 留给下一轮。

2. 理解触发时什么状态需要更新

符号结算操作重置的变量
+ - res += sign * num num = 0，sign 更新为当前符号
* / lastNum = lastNum */ num（不动 res） num = 0，sign 更新为当前符号
( stack.push(res); stack.push(sign)，开启新上下文 res = 0，sign = 1，num = 0
) res += sign * num，然后 pop 合并外层 num = 0
口诀：运算符越多，延迟越多——± 立即结算，±*/ 需缓冲 lastNum，±() 需栈暂存外层上下文。

3. 通用算法模版

3.1 加减法（仅 + 和 -）

结算时机最直接：读到运算符（或末尾），就用上一个 sign 把刚读完的这个数 num 立刻累进 res，随后重置 num，并把当前符号存为新的 sign。无缓冲、无延迟。

// 结算核心（读到 + - 或末尾时触发，sign 是上一个运算符）
if (sign == '+') res += num;
else             res -= num;
num = 0; sign = ch;
时机：被结算的数就是「当前符号前面、刚读完的那个数」。读到符号的瞬间就完成入账，所以循环内已结算完，res 即最终结果，循环外无需收尾。

3.2 四则运算（+ - * /）LeetCode 227

这一版和 3.1 的结算时机完全不同，不要套用，否则容易困惑。包括最后面循环结束还有最后的累加。因为 * / 优先级高于 + -，一个数不能遇到立刻入账——它后面可能还跟着 * / 会继续改变它。于是引入了lastNum。

lastNum 是什么：「当前这一项（term）的待定结果」——还没定死，可能还会被后面的 * / 继续合并。
两级累积：res = 已定死的项之和；lastNum = 正在累积、可能被乘除改变的这一项。

因此结算被拆成三种动作，对应三种触发：

触发（当前符号/末尾）结算动作为什么这样更新
遇 + / -res += lastNum；然后 lastNum = num前一项定死了 → 冲进 res；num 是刚读完的「本符号前面的数」，成为新项的起点
遇 * / /lastNum = lastNum */ num当前项没定死 → 就地合并，优先级高，不碰 res
末尾（i == len-1）先按 sign 结算，循环后再 res += lastNum最后一项没有后面的符号来触发关项，必须手动收尾

看 3 + 5 * 6 + 4 * 2，揭示结算到底有多「晚」（目标 41）：

ichsign(结算用)动作reslastNum
1++res += 0；lastNum = 303
3*+res += 3；lastNum = 535
5+*lastNum = 5 × 6 = 30（仍在 lastNum）330
7*+res += 30；lastNum = 4（此刻 num 已是 4）334
8末尾*lastNum = 4 × 2 = 8338
结束——res += 841—
核心洞见：结算「慢半拍」，关不关项看上次的 sign。
一项是否被冲进 res，不看当前字符 ch，而看上一次的 sign 是不是 ±。当前字符只是扣扳机：
- 扳机用 * / / 扣 → 只做乘法合并，结果留在 lastNum，不关项；
- 扳机用 + / - 扣 → 才把 lastNum 冲进 res，关项。
上表里 5 × 6 = 30 一直到第 7 位的第二个 *（sign=+）才入账，不是第 5 位的第二个 +（那里 sign=*，只算出 30 仍待定）。
对比加减法：加减法读到符号立刻 res += num 即时入账；四则符号被暂存、结算永远慢半拍，那半拍恰好用来凑齐乘法的两个操作数。加减法「即时结算」，四则「乘除延迟、加减才关项」。
两句重点：
① 触发结算是看当前碰到的符号；但结算逻辑看上一个符号（sign）。
② i=5 那个 + 结算的是乘法 5 × 6（sign=*），结果留在 lastNum；等到 i=7 遇 *，用的是 sign=+ → 才 res += lastNum（30 入账）。
结算时 num 存到哪了——它跑在结算前面一步。
同一轮迭代里，数字累加先于结算判断执行（isDigit 在结算 if 之前），所以到达结算那一刻，num 已经把「当前触发位置前面的那个数」完整装好了：
- 触发位置是运算符 → num 保持原样，正是该运算符左边、上一项起点之前累计的那个数；
- 触发位置是末尾字符 → num 已含最后一位，是完整的最后一个数。
因此 num 永远比结算快一步：它装的是下一项的起点，不是本次要入账的数。本次冲进 res 的是 lastNum（上次积下的成果），num 只负责被 lastNum = num 接过去开下一项。用 num 入账会把下一项起点错当成这一项的成果。
（上表 i=7 处：num=4 已跑到 * 前面、即下一项 4×2 的起点；入账的是 lastNum=30。）

3.3 带括号的加减法（+ - ( )）

分派对象变了：3.1 / 3.2 的 switch 分派在上一个符号 sign 上（switch (sign)），当前字符 c 只扣扳机；3.3 的 switch 分派在当前字符 c 上（switch (c)）——c 既扣扳机又选动作。原因：( ) 不是二元运算符，没有「上一个符号管辖的那个数」可结算——( 要保存现场、开启新上下文，) 要先结算内层再合并回外层，这些动作只能由当前字符决定。

int calculateWithParentheses(String s) {
    if (s == null || s.isEmpty()) return 0;

    int res = 0;
    int num = 0;
    int sign = 1;     // 1 代表 +, -1 代表 -
    Stack<Integer> stack = new Stack<>();

    for (int i = 0; i < s.length(); i++) {
        char c = s.charAt(i);

        if (Character.isDigit(c)) {
            num = num * 10 + (c - '0');
        }

        if (c == '+' || c == '-' || c == '(' || c == ')' || i == s.length() - 1) {
            switch (c) {
                case '+': {
                    res += sign * num;
                    sign = 1;
                    num = 0;
                    break;
                }
                case '-': {
                    res += sign * num;
                    sign = -1;
                    num = 0;
                    break;
                }
                case '(': {
                    stack.push(res);
                    stack.push(sign);
                    res = 0;
                    sign = 1;
                    num = 0;
                    break;
                }
                case ')': {
                    res += sign * num;
                    int lastSign = stack.pop();
                    int lastRes = stack.pop();
                    res = lastRes + lastSign * res;
                    num = 0;
                    break;
                }
        }
    }

    return res;
}
关键：遇到 ( 把当前 res 和 sign 入栈，开启新上下文；遇到 ) 先结算括号内，再弹栈合并回外层。sign 用 int 方便入栈。
3.1 / 3.2（无括号）3.3（带括号）
谁扣扳机当前字符 c当前字符 c（不变）
谁选动作switch (sign)——上一个符号switch (c)——当前字符
结算用谁sign（上一个运算符）res += sign * num 里的 sign 仍是上一个运算符（不变）
一句话：变化的是「由谁选动作」——从上一个符号 sign 变成当前字符 c；不变的是「用哪个符号结算」——sign 依旧是上一个运算符。
( 是唯一扣了扳机却不结算的例外：它把当前 res 和 sign 压栈保存外层现场，然后 res = 0 清零开新上下文；) 先 res += sign * num 结算括号内，再弹栈 res = lastRes + lastSign * res 合并回外层。
而 default（i == len - 1 且末尾是数字）那行 res += sign * num，正是「用上一个符号结算」的最终体现——最后那个数还是拿前面的 sign 入账。
