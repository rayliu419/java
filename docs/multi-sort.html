多字段排序：Comparator 综合拼装

核心思路：对象排序的难点不在"排"，而在"比"——class 有多个字段，其中既有可直接比较的基本字段（int value），又有需要转换后才能比较的处理字段（String "xx:yy:zz" → 秒）。关键问题是：怎么把多个字段的规则综合拼装成一个 Comparator？本仓库的 MultiSort 采用「外围连接」：每个字段一个独立小比较器，转换逻辑内聚在比较器内部，再用 thenComparing 按优先级串联成字典序。

1. 问题背景：为什么多字段排序是面试高频

算法题里的排序，对象排序比 int 数组排序常见得多。一出现"先按 A 排，A 相同再按 B 排"的描述，就属于多字段排序（Multi-key Sort）。典型场景：

  • 区间类：先按起点排，起点相同再按终点排（Merge Intervals、Meeting Rooms）
  • 包络类：先按宽排，宽相同再按高排（Russian Doll Envelopes）
  • 日志类：先按类型排（字母日志 / 数字日志），类型相同再按内容排（Reorder Data in Logs）
  • 业务类：先按优先级排，再按时间排（本仓库 MultiSort：value → time）

这类题的考察点不在排序算法本身（就是 Arrays.sort），而在如何把多条比较规则组装成一个 Comparator——这也是本节要讲透的东西。

2. 难点拆解：两类字段，两种"比法"

一个待排序 class 的字段天然分成两类：

字段类型例子比较方式典型写法
基本字段int value直接比较大小Comparator.comparingInt(Item::getValue)
处理字段String time = "xx:yy:zz"先转换（解析成秒）再比较独立字段比较器，内部调用转换函数
多字段组合value + time按优先级串联成字典序comparingInt(...).thenComparing(timeComparator)
核心心法：把两个问题彻底分开——
  1. 每个字段怎么比：基本字段一行搞定；处理字段把"转换"封装进该字段的比较器，比较器只管自己的事；
  2. 字段之间怎么连：用 thenComparing 按优先级链式连接，前一个返回 0 才进入下一个，天然就是"先 value、相等再 time"的字典序。

3. 三种 Comparator 拼装方式对比

方式一：手写整体 compare（不推荐）

// 所有规则堆在一个 compare 里，嵌套 if-else
Arrays.sort(items, new Comparator<Item>() {
    @Override
    public int compare(Item o1, Item o2) {
        if (o1.getValue() != o2.getValue()) {
            return o1.getValue() - o2.getValue();
        }
        int t1 = getTime(o1.getTime());
        int t2 = getTime(o2.getTime());
        if (t1 != t2) {
            return t1 - t2;
        }
        return 0;
    }
});

字段一多，这个 compare 会越来越长：每一级字段都要一层 if 包裹，缩进失控，哪个字段在哪一层一目难辨。改排序规则时要小心翼翼，极易改错层级。

方式二：外围连接（本实现采用，推荐）

// 每个字段一个独立比较器，thenComparing 串联
Comparator<Item> timeComparator = (o1, o2) -> getTime(o1.getTime()) - getTime(o2.getTime());
Comparator<Item> c = Comparator.comparingInt(Item::getValue)
        .thenComparing(timeComparator);
Arrays.sort(items, c);

优点：加字段 = 加一个比较器 + 加一个 thenComparing，层级由链式结构天然表达；处理字段的转换逻辑内聚在字段比较器内部，与排序主流程解耦。

方式三：预计算 key（key extraction）

// 先统一把处理字段转成可直接比较的值，再直连
for (Item item : items) {
    item.setTimeSec(getTime(item.getTime()));
}
Comparator<Item> c = Comparator.comparingInt(Item::getValue)
        .thenComparingInt(Item::getTimeSec);
Arrays.sort(items, c);

转换从"每次比较都做"变成"每个元素只做一次"，比较成本更低；代价是给 Item 多一个字段（或外部 map 存 key），多一层预计算循环。元素量大、转换代价高时值得用。

维度方式一：手写嵌套方式二：外围连接方式三：预计算 key
代码可读性差，层级靠缩进表达好，链式即层级好
加字段 / 改规则易错，要动嵌套结构加一个比较器 + 一个 thenComparing加一行 comparingXxx
转换成本每次比较都转换每次比较都转换每元素只转换一次
侵入性无无需改类结构 / 额外容器

4. 外围连接逐步拆解（MultiSort 源码）

对应文件：algorithm/src/main/java/leetcode/MultiSort.java（测试：algorithm/src/test/java/leetcode/MultiSortTest.java，从 engineering 包迁移而来）。

第一步：待排序对象 Item

static class Item {
    private int value;   // 基本字段：直接比较
    private String time; // 处理字段："xx:yy:zz"，需转秒
    // getter / setter 略
}

第二步：转换函数独立成方法

public static int getTime(String time) {
    String[] res = time.split(":");  // ":" 是正则字面量，可直接拆分
    return Integer.parseInt(res[0]) * 3600 +
            Integer.parseInt(res[1]) * 60 +
            Integer.parseInt(res[2]);
}

"xx:yy:zz" → 秒（时 × 3600 + 分 × 60 + 秒）。独立成方法的意义：比较器内部只是"调用它"，比较逻辑与解析逻辑互不干扰，还能单独写单测（testGetTimeNormal 等覆盖 6 个转换用例）。

第三步：处理字段单独一个比较器

Comparator<Item> timeComparator = (o1, o2) -> getTime(o1.getTime()) - getTime(o2.getTime());

这个比较器只做一件事：把两个 time 转成秒再比大小。转换逻辑被关在字段比较器内部，主流程完全看不到解析细节。

第四步：thenComparing 串联（外围连接）

Comparator<Item> c = Comparator.comparingInt(Item::getValue)
        .thenComparing(timeComparator);
Arrays.sort(items, c);
thenComparing 的语义：前一个比较器返回 0 时，才进入下一个比较器。这正好实现"先按 value 排，value 相等再按 time 排"——不需要任何 if-else，优先级由链条顺序表达，这就是"外围连接"。

排序结果验证

以混合用例（testSortMixedValuesAndTimes）为例：输入 value/time 为 (2,23:59:59) (1,00:00:01) (2,00:00:00) (1,23:59:59)，排序后 (1,00:00:01) (1,23:59:59) (2,00:00:00) (2,23:59:59)——value 优先，同 value 按时间升序。另外 Arrays.sort 是稳定排序，value、time 都相等时保持原相对顺序（testSortStableWhenValueAndTimeEqual）。

5. 面试真题延伸

同一个"外围连接"套路，改改字段比较器就能套进一堆真题：

题号题目排序规则要点
56Merge Intervalsstart 升序合并只需要第一键，先排序是前提
354Russian Doll Envelopesw 升序 + h 降序第二键要降序，配合 LIS 求最大嵌套
937Reorder Data in Log Files先类型、再内容"类型"也是需要处理的字段（判断 letter/digit）
179Largest Number拼接比较比较函数本身复杂：(a+b).compareTo(b+a)
973K Closest Points to Origin距离升序距离是计算字段，适合预计算 key

降序怎么做：reversed() 的位置是考点

// 错误：把整个链条 reversed，value 也变降序了
Comparator.comparingInt(Item::getValue).thenComparing(timeComparator).reversed();

// 正确：只对"要降序的那一个字段比较器" reversed
Comparator<Item> hDesc = Comparator.comparingInt(Item::getH).reversed();
Comparator<Item> c = Comparator.comparingInt(Item::getW).thenComparing(hDesc);

6. 易错点清单

易错点 1（仓库早期实际踩过的坑）：转换函数参数写错。 早期版本用 commons-lang3 的 StringUtils.split(":")——单参重载按空白拆分，":"被当成待拆分的字符串本身，返回 [":"]，随后 Integer.parseInt(":") 抛 NumberFormatException；参数 time 完全没用上。正确写法是 StringUtils.split(time, ":")（按分隔符拆分）。当前实现改用 JDK 的 time.split(":")（":" 是正则字面量，可安全拆分）。写转换函数时务必确认：拆的是参数，不是字面量；用的 API 语义对吗？
易错点 2：减法比较的溢出。 getTime(o1) - getTime(o2) 在值很大（如秒数接近 Integer.MAX_VALUE）时会溢出，得到错误结果甚至负负得正。用 Integer.compare(a, b) 或 comparingInt 更稳。本用例时间最大 86399 秒，无风险，但面试中值得主动指出。
注意：处理字段为 null 时，split 返回 null，res[0] 抛 NPE；格式不校验（"12:99:99" 也能解析）。是否需要防御视题目约束而定，面试时提一句"假设输入格式合法"即可。
提示：理解 compare 返回 0 的含义——它表示"本轮不分胜负"，此时才轮到下一个比较器，而不是"两个对象相等"。排序完成后，compare(a,b) == 0 的一批元素称为"等价类"，稳定排序保证它们保持原始相对顺序。

7. 总结

外围连接三步法：
  • 拆字段：按优先级列出每个字段，标注它是基本字段还是处理字段；
  • 写比较器：基本字段用 comparingXxx；处理字段单独写一个比较器，转换逻辑内聚在内部；要降序就在该字段比较器上 reversed()；
  • 链式串联：comparingInt(...).thenComparing(timeComparator).thenComparing(...)，链条顺序 = 排序优先级，天然字典序。
需要多次比较的高代价转换（解析、距离计算）用"预计算 key"先转好，thenComparingInt 直连。
